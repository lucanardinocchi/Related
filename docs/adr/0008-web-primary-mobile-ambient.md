# Web becomes the primary surface; mobile narrows to ambient capture

**Supersedes [ADR-0007](0007-split-web-mobile-frontends.md).** Inverts the web/mobile product split decided in ADR-0007. `src/web/` (Next.js 15 App Router) is now the **primary surface** carrying the full domain CRUD: Relationships, Groups, Contacts (with rich profile fields — birthday, area, occupation, education), Interactions, Open Threads / Commitments, Candidate Actions, a unified Calendar (Interactions + external Google events), and a text+voice Agent chat. `src/mobile/` (Expo / React Native, iOS-primary per ADR-0006) narrows to an **ambient-capture surface**: HealthKit Sleep signal, in-pocket voice with the agent, push notifications, sign-in, and read-only browsing of state captured on web. `src/shared/` and `src/backend/` are unchanged structurally — both apps continue to consume the same `@related/shared` clients and Supabase backend.

## Considered options

- **Keep ADR-0007 as written** — web stays narrow (Sign-in, Connect Calendar, User Context editor, Voice agent); mobile owns CRUD. Rejected: the User's reflective work (sit-down editing of contact profiles, browsing relationship history, planning Commitments, scrubbing a unified Calendar) is desktop-shaped, not phone-shaped. The Notion-style information architecture the redesign targets — wide sidebar, multi-column detail pages, table-like grids — does not collapse to a phone gracefully. Forcing CRUD primarily onto mobile blocked the User's day-to-day usage pattern.
- **True parity across web and mobile** — both apps offer the same CRUD surface, just with platform-appropriate UI. Rejected: doubles the UI surface to maintain, and most CRUD has no genuine value on a phone for this product (the User isn't editing a Contact's occupation while walking down the street). Parity also obscures which surface drives design.
- **Web-first now, mobile catches up later as parity** — same end state as the chosen option, but framed as a temporary inversion. Rejected as framing: there is no concrete plan to bring mobile back up to CRUD parity, and pretending otherwise creates ambiguity about where new features should land. The split is intended to be durable, not transitional.
- **Collapse mobile entirely and ship web only** — drop `src/mobile/` workspace. Rejected: HealthKit Sleep signal (ADR-0001, ADR-0006) requires an iOS native module; in-pocket voice and lock-screen push are genuinely mobile-shaped capabilities the agent loop depends on. Mobile narrows but does not disappear.

## Why

The User's relationship-intelligence work is **reflective, not ambient on their part**. They sit down at a desk, look at a person, edit context, plan a commitment, scan their calendar, browse history. That work is desktop-shaped. The agent's work is the part that is genuinely ambient and mobile-friendly — running passes in the background, surfacing voice suggestions in-pocket, sending a push when something is salient. ADR-0007 split the two correctly but assigned the surfaces the wrong way: CRUD ended up on the phone (cramped, transient, the wrong context for reflection) while the desktop got the narrow voice prototype. ADR-0008 inverts.

`@related/shared` already exports framework-agnostic clients, so the inversion costs no domain-logic duplication — only a presentation-layer rebuild on web (which is happening as part of this change anyway) and a future narrowing of mobile screens (separate follow-up, not in this PR).

## Consequences

- **Web feature set expands dramatically.** New routes land in this PR: `/relationships` (index with analytics + sort/filter), `/relationships/[id]` (individual detail with Key Details, Recent Context, Analytics, Full History), `/groups/[id]` (mirrored), `/calendar` (unified Interactions + Google events, badged by source), `/commitments` (Open Threads filtered to `me_owes_them` with `origin` + `communication_status` axes), `/agent` (text+voice chat, replaces `/talk`). Existing `/context` and `/onboarding` retheme but keep their behaviour.
- **Mobile is not removed, but stops being the design driver.** A follow-up issue will narrow `src/mobile/` to the ambient-capture surface (HealthKit, voice, push, sign-in; CRUD screens either removed or rendered read-only). Until then, mobile keeps its existing CRUD usable — no functional regression for anyone on iOS today, just no new mobile-only features.
- **`@related/shared` gets richer.** This change adds: profile fields to `Contact`; UPDATE/DELETE methods across `RelationshipsClient`, `GroupsClient`, `InteractionsClient`; commitment axes (`origin`, `communicationStatus`) on `OpenThread` with `listCommitmentsForUser` and `setCommitmentMeta`; a new read-only `CalendarEventsClient` exposing `inferred_signal_calendar`; pure analytics helpers under `src/shared/src/analytics/`.
- **Three new backend migrations** land: rich contact profile fields (additive on `contacts`), commitment axes on `open_threads` (additive, nullable `origin`, defaulted `communication_status`), and the missing UPDATE/DELETE RLS policies on `contacts`, `relationships`, `groups` that were blocking edits at the DB layer (relationships' `role`/`cadence` columns existed since slice 8 but were unreachable from authenticated clients).
- **Glossary updates.** `Open Thread` in [src/shared/CONTEXT.md](../../src/shared/CONTEXT.md) is amended to reflect that it now carries the commitment lifecycle metadata; a new **Commitments view** entry clarifies that the `/commitments` UI is a filtered view over Open Threads where `direction = me_owes_them`. `Contact` is amended for the new optional profile fields. `Calendar` is amended to clarify the unified web view (Interactions + Google events badged by source) versus the agent's `Calendar density` signal (which remains separate).
- **Vercel deploy is unchanged structurally** — still Next.js, still `@related/web` workspace, still the same env vars set during the ADR-0007 transition. The Vercel-side migration noted in [docs/DEPLOY.md](../DEPLOY.md) Tier 0 is fully done.
- **Mobile env vars stay** (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`) for as long as mobile builds keep running.
- **No data migration.** Every backend change is additive — existing Open Threads default to `communication_status = 'not_communicated'` and `NULL` `origin`, which is correct for non-commitment threads (e.g. `direction = they_owe_me`); existing Contacts keep their three columns and get four new nullable ones.
